### Finding — `uv run pip list` reports the wrong environment

While running check e the venv's numpy was seen as `2.5.1`, which contradicts the `1.26.4`
that check d's `import numpy` reports. The cause:

```
$ uv run which pip
/usr/bin/pip
```

The project venv has no `pip` in it, so `uv run pip` resolves the name on `PATH` and runs
**Fedora's system pip**, which lists the system's own packages. Nothing was installed into
the system and nothing was wrong with the venv. `uv pip list` (uv's own, no `run`) targets
the project venv correctly and shows `numpy 1.26.4`, `protobuf 4.25.9`,
`torch 2.14.1+cpu`, `apache-tvm 0.26.0`, `onnxruntime 1.27.0`.

Worth a line in the docs later: `uv pip list`, never `uv run pip list`. Anyone auditing a
broken venv with the wrong command will chase a phantom.

```
File ".../inference.py", line 55, in _load_tvm

File ".../tvm/support/cc.py", line 365, in _linux_compile
    proc = subprocess.Popen(cmd, ...)
File "<frozen posixpath>", line 152, in dirname
TypeError: expected str, bytes or os.PathLike object, not NoneType
assert 1 == 0  where 0 = CompletedProcess(args=['/work/.venv/bin/python', 'inference.py'],
                                          returncode=1).returncode
```

### Why, confirmed rather than guessed

`load_module` builds a `.so` from the packaged `model_tvm.tar`, which needs a C compiler.
TVM's `_linux_compile` received `cc=None` and fell over computing the compiler's dirname.
Confirmed directly:

```
$ podman run --rm ubuntu:24.04 bash -c "command -v gcc g++ cc || echo 'NO C COMPILER PRESENT'"
NO C COMPILER PRESENT

$ command -v gcc g++ cc      # Fedora host
/usr/bin/gcc
/usr/bin/g++
/usr/bin/cc
```

So the failure is environmental, not a product or dependency defect: the stock image has no
toolchain and the laptop does.

### Finding the spec did not anticipate

**A TVM deployment package needs a C compiler on the target device.** `README.md:284-290`
tells the user to `pip install -r requirements.txt` and run `python inference.py` on the
device, and nothing anywhere states that a compiler is required when the winning candidate
is a TVM one. On a Pi or an ARM box without `build-essential`, the packaged artifact will not
load and the failure surfaces as that same opaque `TypeError`.

This is a documentation and packaging gap, not something to patch here: it touches
`README.md` beyond T6's scope and arguably `api/packager/generator.py`, which builds the
package. Best home is the findings register from P0.3, or the device/packaging spec. It is
recorded, not acted on.
