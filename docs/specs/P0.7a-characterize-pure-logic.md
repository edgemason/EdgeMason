# P0.7a: Characterization tests for the pure decision logic

**Depends on:** P0.6 (uses `tests/support/golden.py` and `normalize`)
**Gate class:** identical (tests only; they lock **current** behaviour, quirks included)
**Executor:** follow `docs/specs/EXECUTOR.md`.

## Why
Every later refactor must provably leave the decisions unchanged: which candidates get planned, how they are ranked, what is estimated for the target, which provider is used, how data is split, and which models are rejected. Today these decisions are tested only loosely or not at all (PLAN section E). Here, "characterization" means: **assert what the code does now, not what it should do.**

## Scope (new test file only)
- `tests/test_characterize_logic.py`
- `tests/golden/*.json` files created by this test file (first run creates them; review them, then commit)

## Out of scope
- Any change to `api/`. If the current behaviour looks like a bug, **lock it anyway** and add a `# QUIRK:` comment explaining it. Then list it in your report.

## Test cases
Every golden name below is a file under `tests/golden/`.

### 1. Planner: `api.planner.rule_based.generate_candidates(PlannerInput(...))`
Build a full matrix and lock the **entire returned dict** in golden `planner_matrix`, as a list of `{"input": {...}, "output": {...}}`:

| Field | Values |
|---|---|
| `operator_counts` | CNN `{"Conv": 10, "Relu": 10}`; matmul `{"MatMul": 10, "Add": 10}`; unknown `{"Relu": 5}`; tie `{"Conv": 5, "MatMul": 5}` |
| `model_size_mb` | 1.0, 5.0 (the threshold), 50.0 |
| `has_calibration_data` | True, False |
| `include_tvm` | True, False |
| `max_latency_ms` | None, 50.0, 100.0 (the threshold), 500.0 |

That is 4×3×2×2×4 = 192 cases. Read the `PlannerInput` fields from `api/planner/rule_based.py` and use only those.

### 2. Ranking: `api.services.ranking.rank_results`
- Build 5 synthetic results in exactly the dict format `pipeline._evaluate_candidate` returns:
  - keys `candidate`, `benchmark`, `estimate`, `accuracy`, `model_path`, `provider`, `error`
  - distinct latency, memory and accuracy values
  - **one** has `benchmark.success=False`
  - **one** has `accuracy=None`
  - **two** have identical latency, to test the tie order
- For each priority (`latency`, `memory`, `accuracy`, `balanced`, plus an unknown string `"bogus"`) × constraints (none; `max_latency_ms` excluding one; `max_memory_mb` excluding one; both): lock the returned **order of candidate names** in golden `ranking_matrix`.
- **Also assert** (no golden): when every result fails its constraints, the result is `[]`.

### 3. Target estimate: `api.services.hardware.estimate_on_target`
For every hardware id in `profiles/hardware_profiles.json` (`rpi3`, `rpi4`, `rpi5`, `jetson_nano`, `x86_64`) × quantization (`fp32`, `dynamic_int8`, `static_int8`, `"unknown_q"`), with `latency_p50_ms=10.0` and `memory_mb=100.0`: lock the full returned dict in golden `estimate_matrix`.

### 4. Execution-provider selection: `api.services.hardware.select_execution_provider`
- Monkeypatch `api.services.hardware.ort.get_available_providers` to return either `["CPUExecutionProvider"]` or `["CUDAExecutionProvider", "CPUExecutionProvider"]`.
- For every hardware id × requested (`auto`, `cpu`, `cuda`) × `include_tvm` (True, False) × installed (2 options): record either `{"result": "<provider>"}` or `{"error": "<ValueError message>"}`.
- Lock this in golden `provider_matrix`.

### 5. Data split and warnings: `api.optimizer.validation`
- **`split_calibration_and_test`.** For sample counts [2, 3, 10, 100, 333, 1000], with `ValidationData(inputs=np.arange(n*4, dtype=np.float32).reshape(n, 4), labels=np.arange(n))`, record:
  - `calibration_count`
  - `test_count`
  - the **first 10 test labels**
  - the sorted calibration row sums

  Lock this in golden `split_matrix`.
- **`data_warnings`.** For `(calibration_count, test_count)` in [(1, None), (50, None), (100, None), (300, None), (5, 10), (50, 150), (100, 199), (100, 200), (300, 700)]: lock the returned lists in golden `data_warnings_matrix`.
- **Limits** (assert error messages exactly; no golden):
  - `load_validation_data` on an `.npz` with 1001 samples → the "1-1000 samples" error.
  - Monkeypatch `api.optimizer.validation.MAX_VALIDATION_BYTES` to 1000, then load a 2000-byte npz → "validation data is too large".
  - An npz with an extra key → the "only inputs and labels" error.
  - Labels that are float, or negative, or a different length from inputs → each gives its exact message.
  - Inputs that are float64, or contain NaN → each gives its exact message.

### 6. Model validation: `api.services.model_validation.validate_model`
Build tiny ONNX models with `onnx.helper` (pattern: `tests/conftest.py`) and assert the exact `ValueError` message, or that no error is raised:

| Model | Expected |
|---|---|
| valid: 1 float input `[1, 4]` | passes |
| dynamic batch `["N", 4]` | passes |
| 2 graph inputs | "single-input models only" |
| int64 input | "float32 model inputs only" |
| dynamic non-batch dim `[1, "H"]` | "only the model batch dimension may be dynamic" |
| a dim of 4097 | "model input dimension is too large" |
| `MAX_INPUT_ELEMENTS` monkeypatched to 3 with input `[1, 4]` | "model input tensor is too large" |
| `MAX_MODEL_NODES` monkeypatched to 1 with a 3-node model | "model has too many nodes" |
| an initializer that is also listed in `graph.input` | treated as a non-input; passes |

**Monkeypatch the names where `model_validation` reads them:** `api.services.model_validation.MAX_INPUT_ELEMENTS` and `api.services.model_validation.MAX_MODEL_NODES`, not `api.config`.

