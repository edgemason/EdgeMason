# P2.6: Pilot sweep runner (configs → measured + additive prediction)

**Type:** feature (approved by user on 2026-11-14)
**Depends on:** P2.3 (fetcher: per-layer + boundary tables), P2.4 (real int8 kernels), P2.5 (mixed generator). Absorbs **B-59** (failed runs recorded, not dropped).
**Gate class:** intended improvement — produces a findings register with, per config, the measured latency, the additive prediction, and the seam count, on a sweep that spans few→many seams; no run is silently dropped.
**Status:** agreed
**Executor:** follow `docs/specs/EXECUTOR.md`. **Acceptance includes the lint ratchet** (`BASE_REF=origin/main scripts/lint_ratchet.sh`), not just pytest.

## 1. Goal
This is the pilot's data-collection block. It builds many mixed-precision models spanning few→many seams, measures each end-to-end, computes the **additive** prediction for each, and records everything in one findings register. The graph-aware cost model and the predicted-vs-measured verdict are the *next* block; this block produces the data they need (and the additive baseline to beat).

**Done** = running the sweep on one model (x86 first) writes a findings register with one row per config: config id, fp32 node list, seam count, measured p50/p90, additive prediction, and a status — and a killed/failed run appears as `status: failed`, never missing.

## 2. Schema
**Lookup table (built once, step 0).** Run the P2.3 fetcher on the **pure fp32** and **pure int8** models → `{layer_name: {fp32_us, int8_us}}`. This is the additive model's source.

**Config.** A list of fp32 node names (from `Quantizer.excludable_node_names`). Everything else is int8.

**Sampling (stratified — option A).** Vary two knobs to span the seam axis:
- **count** — how many layers are kept fp32 (0, a few, … up to all);
- **placement** — clustered (adjacent fp32 layers → fewer seams) vs spread (interleaved → more seams).
Target ~40 configs total, seeded for reproducibility. The **seam count is measured from the built model** (count of Q/DQ boundary nodes in the fetcher's boundary table) — it is recorded, not assumed.

**Per-config pipeline.** For each config: `create_mixed_int8` (P2.5) → fetcher (compute + boundary tables) → time end-to-end with the bench protocol (warm-up, min timed runs, budget) → compute:
- `measured_p50`, `measured_p90` (µs);
- `additive_pred = Σ lookup[layer][fp32_us if layer∈fp32_list else int8_us]`;
- `seam_count` (from boundary table);
- `status` ∈ {ok, failed} with an error string when failed.

**Findings register (output).** One row per config (JSON lines or CSV), schema fixed and documented in the spec. Deterministic given the seed.

## 4. Behaviour (tests first)
| # | Given | When | Then |
|---|---|---|---|
| 1 | a model + seed | generate configs | the sweep spans a range of seam counts (not all clustered at one value); count is reproducible for the seed |
| 2 | one config | run it | the register row has measured p50/p90, additive_pred, seam_count, and status `ok` |
| 3 | a config whose build or run fails (simulate a raise / nonzero exit) | run the sweep | that row is recorded `status: failed` with the error; the sweep continues; the row is **not dropped** (B-59) |
| 4 | a known lookup table + a known fp32 list | compute additive_pred | equals the exact hand-summed value (unit test, no model run) |
| 5 | `fp32_list = []` | run | seam_count 0 and the model equals pure int8 (ties to P2.5 #1) |

## 5. Failures
| Case | Action |
|---|---|
| A config's `create_mixed_int8` raises (e.g. bad name) | record `status: failed` + error; continue the sweep |
| A run is killed / OOM / writes no result (B-59) | record `status: failed` with exit info; never drop the row |
| Fetcher can't parse a trace | record `status: failed` with reason |
| A layer in a config is missing from the lookup table | **stop**, raise — the additive prediction would be wrong, not just noisy |
| Pure fp32 / pure int8 lookup build fails | **stop**, raise — no lookup means no additive baseline |

## Amendment A (2026-11-14): the lookup must live in the same execution regime as the measurement

**Why.** The first sweep produced a nonsensical result: additive MAPE ≈ 97% and additive error that
*fell* as seams rose (corr = −0.47). Root cause found in `_fetch_tables`:
`options.graph_optimization_level = ORT_DISABLE_ALL`. The lookup is profiled with **all
optimizations off** (chosen so every node stays visible for name mapping), while the measured side
runs the **fully optimized** benchmark. Under `DISABLE_ALL` the int8 `MaxPool` runs a slow reference
path (~18× slower; 11623 µs vs 657 µs fp32), so the int8 lookup sums to 8444 µs while the real
optimized int8 measures 2156 µs. The additive baseline and the measurement were in two different
worlds — the result is an artifact, not an H1 signal.

**The trade-off (must be handled, not ignored).** Turning optimizations on fixes the timing but
**fuses nodes and changes names**, so the compute/boundary name mapping gets harder. The fix is not a
one-line flip.

**Required changes:**
1. **Profile the lookup in the optimized regime** — the same `graph_optimization_level` the benchmark
   uses (not `ORT_DISABLE_ALL`). Apply the same to the per-config `_fetch_tables` calls, so every
   per-layer number lives in the benchmark's world.
2. **Handle node-name mapping under fusion** — with optimizations on, some nodes merge/rename. Map at
   the surviving-node level (e.g. `QLinearConv` persists). Keep the P2.5 reject-unknown discipline:
   a layer that can't be mapped stops the build, never a silent wrong attribution.
3. **Add a hard sanity gate (the check that would have caught this):** after building the lookup,
   assert **pure-int8 additive ≈ pure-int8 measured** and **pure-fp32 additive ≈ pure-fp32 measured**,
   each within a tolerance (e.g. ≤ 15%). If either fails, **stop and report** — do not run the sweep.
4. **If the sanity gate still fails even optimized** (because enabling profiling can itself defeat
   some fusions): fall back to **calibrating** per-layer times to measured latency — fit one scale so
   the pure configs match — and use the calibrated per-layer costs for both the additive and the
   graph-aware models, so the comparison stays fair. Record which path was used in FINDINGS.
5. **Re-run the sweep** (seed 0, same config set) and re-record the register. The new register is the
   real pilot data.

**Acceptance additions:** a unit test for the sanity gate (a deliberately mismatched lookup must
raise), plus the existing ratchet + pytest. The optimized-regime numbers go in `docs/research/FINDINGS.md`.
