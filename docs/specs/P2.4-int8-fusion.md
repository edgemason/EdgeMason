# P2.4: Make static INT8 use real integer kernels (fuse, don't just wrap)

**Type:** feature (approved by user on 2026-11-14)
**Depends on:** P2.3 (the fetcher is how we verify the fix), B-62 (the finding this closes)
**Gate class:** intended improvement — on a device that supports it, the quantized model's convolutions execute as **integer** kernels (`QLinearConv`/`ConvInteger`) instead of fp32 `Conv` wrapped in Q/DQ, and INT8 Conv time is **lower** than FP32 Conv time. Verified by the P2.3 fetcher trace.
**Status:** agreed
**Executor:** follow `docs/specs/EXECUTOR.md` (its absolute limits always apply).

## 1. Goal
Today `create_static_int8` produces a QDQ graph that ORT does not fuse on the x86 host: every `Conv` still runs in fp32, wrapped in Dequantize/Quantize, so INT8 is pure overhead (B-62). In the analogy: the translators were hired but the team kept working in the slow language.

This spec changes the quantizer so the int8 path is **actually used** — ORT (or TVM later) runs genuine integer convolution kernels — giving int8 a real compute saving. Only then does a mixed-precision trade-off exist for the additive-vs-graph pilot to study.

**Done** = running the P2.3 fetcher on the re-quantized model shows the convolutions as integer kernels, and int8 Conv time < fp32 Conv time, **on at least one target device**. (See §5: the x86 host may be unable to fuse; the Pi 5, with dot-product instructions, is the authoritative check.)

## 2. Schema
The change is to `Quantizer.create_static_int8` config only. Candidate knobs to test (the executor picks the combination that makes the fetcher show integer kernels, and records which worked):
- `activation_type=QuantType.QUInt8` (keep `weight_type=QuantType.QInt8`, `per_channel=True`) — ORT's CPU MLAS `QLinearConv` expects **uint8** activations; s8s8 on non-VNNI x86 falls back to fp32.
- and/or `quant_format=QuantFormat.QOperator` to emit `QLinearConv` directly rather than relying on QDQ fusion.
- `reduce_range=True` where the existing code comment (`quantizer.py:~123`) says it is needed on non-VNNI x86.

No change to the function signature or its return type (still a path to the `.onnx`).

## 3. Scope
**May create or change:**
- `api/optimizer/quantizer.py` — `create_static_int8` config only.
- `tests/` — a test that asserts the quantized model runs integer conv kernels (via the fetcher / trace op type), plus the existing accuracy check.

**Out of scope (do not touch):**
- `api/packager/templates/bench.py`, `api/optimizer/benchmark_engine.py`, `api/optimizer/fetcher.py` (P2.3).
- TVM paths (P2.2 owns those).

## 5. Failures
| Case | Action |
|---|---|
| New config makes ORT emit integer kernels on x86 | success — record which knobs worked in the executor report and in FINDINGS.md |
| x86 still won't fuse (hardware lacks VNNI) | **not a failure of the code** — document it, defer the speed gate to the Pi 5, keep the config that fuses *there*. Never fake the result. |
| Accuracy drops below the recorded tolerance | **stop**, report — a fast but wrong model is not a win |
| `quantize_static` rejects the config combination | **stop**, report the exact error; try the next documented combination |

Every new measured number (int8 vs fp32 Conv time, accuracy) must be recorded in `docs/research/FINDINGS.md` per CODING_STANDARDS rule 6, and B-62 closed with a pointer to it.
